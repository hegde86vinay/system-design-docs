Executive Summary

This document is a practitioner-grade Architect-level FAQ for Sterling OMS interviews — the kind of depth expected at Tech Manager 2 / Senior Manager / Director / Principal Architect rounds at retail GCCs (lululemon, Walmart Global Tech, Fidelity, Target, Tesco, Macy's). It assumes you already know what an order pipeline, agent, or YFS_ORDER_HEADER is. The focus here is: how do you scale, modernize, and architect around Sterling, not how do you configure it.

Distributed OMS

Sterling as the system-of-record + microservices around it for read/write scale. Strangler Fig modernization.

Inventory Systems

GIV is the truth, but availability lookups must serve 10K+ RPS — that requires a separate read-side system.

Fulfillment Optimization

Sourcing across 1500+ stores + 5 DCs + 3PLs with cost, capacity, distance, and split-shipment minimization.

Event-Driven OMS

Kafka backbone with Sterling events bridged via MQ → Kafka. CDC (Debezium) for legacy table reads.

Store Fulfillment

BOPIS, Ship-from-Store, Curbside — all need store associate apps, capacity planning, and SLA tracking.

Modernization Patterns

Anti-Corruption Layer, Strangler Fig, CQRS for reads, Saga for cross-service consistency.

How to use this doc in an interview

Each system design has a high-level diagram + sequence flow. Each Q&A starts with a 30-second elevator answer, then drills into the architect-level depth. Anchor your answers in real Sterling primitives (YFS_TASK_Q, RTAM, changeOrder API, GIV, scheduleOrder agent) — that's the interviewer's signal that you've actually run Sterling in production, not just read about it.

PART I

System Designs — 8 Core OMS Subsystems

Each design below has been sized for a tier-1 retailer: ~100K orders/day, 5M SKUs, 1500+ stores, 5 DCs, peak 50× during Black Friday / EOSS / Diwali sales. The architecture is opinionated — every choice has a "why not" implicit in it.

SD-01

Inventory Availability Service

Read-heavy · 50K RPS

Problem

Every PDP view, cart add, checkout, and search filter calls "is this SKU available, where, and how many?" Sterling GIV (YFS_INVENTORY_SUPPLY + YFS_INVENTORY_DEMAND + ATP rules) is authoritative but DB-bound. At 50K+ availability lookups per second, hitting Sterling directly will melt the Oracle DB.

Key Design Decisions

  • 3-tier cache: Caffeine (in-process) → Redis (cluster) → DynamoDB (durable rollup). Each tier absorbs >90% of misses from the next.
  • Pre-aggregated rollup: Storage pattern {sku}#{pincode} with available qty across all eligible nodes (DC+stores within ship-radius). Avoids fan-out at read time.
  • Event-driven invalidation: Sterling RTAM emits INVENTORY_CHANGE events → MQ → Kafka bridge → consumer updates L3 + invalidates L2. P99 propagation < 2s.
  • Stale-while-revalidate: Better to show 5-second-old data than to time out. Hard refresh only on add-to-cart.
  • Reservation-aware: Subtract soft holds (cart reservations) from displayed qty to reduce oversell at PDP level.

Data Model (DynamoDB)

PK = "AVAIL#{sku}"
SK = "PIN#{pincode}"
Attributes:
  available_qty       : N
  node_breakdown      : L  [{node:"DC01", qty:30}, {node:"STR_BLR042", qty:12}]
  last_refresh_ts     : N  (epoch ms)
  reservation_holds   : N  (cart soft holds)
  network_eligible    : BOOL
  ttl                 : N  (auto-expire 1hr → forces re-read from GIV)
Anti-pattern: Hitting GIV directly from web tier

Every failed Black Friday OMS post-mortem includes this. RTAM is an operational API — it was never designed for 10K+ RPS PDP traffic. Always front it with a CQRS read model.

SD-02

High-Scale Order Orchestration

Stateful · Long-running

Problem

An order is a long-running stateful process: captured → validated → reserved → released → scheduled → shipped → delivered → invoiced. Sterling does this via the order pipeline + YFS_TASK_Q + scheduled agents (scheduleOrder, releaseOrder, etc.). At 100K+ orders/day with peaks 5× higher, the YFS_TASK_Q becomes the bottleneck and pipeline determination logic gets unwieldy.

Scaling Levers

  • Workflow sharding: Temporal partitions by order_id hash → linear horizontal scale.
  • Sterling write throttling: ACL batches changeOrder calls into bulk APIs (Sterling supports up to 200 orders/call) — reduces DB locking on YFS_ORDER_HEADER.
  • Idempotency: Every Activity is idempotent via (order_id + step_id) key in Redis dedup table.
Pragmatic alternative

If your org isn't ready for Temporal, the same outcome is achievable with Kafka Streams + state stores for stateless steps, and Sterling pipelines for the stateful orchestration. Temporal is a 12–18 month adoption.

SD-03

BOPIS Fulfillment System

Store-aware · SLA-driven

Problem

Buy Online, Pick up In Store (BOPIS) requires: (1) showing only stores with the item in stock and within pickup SLA, (2) reserving against a specific store node, (3) routing the pick task to the store associate, (4) tracking pickup-ready / picked-up state, and (5) handling no-show + return-to-stock. Failure modes are visible and brand-damaging — customer drives to the store, item isn't there.

Key Design Decisions

  • Store capacity as a constraint: A store can only pick N orders/hour. Sourcing logic must respect store_pick_capacity alongside inventory. Without this, popular stores get overwhelmed during peak.
  • Soft reservation at PDP, hard at order: When customer selects a store, soft-reserve in Redis (5 min TTL). On checkout, convert to hard reservation in Sterling.
  • Pick task = Sterling shipment: Model as a single-line shipment with ShipNode = StoreNode. Reuse Sterling pick/pack/ship pipeline; UI is the store associate app.
  • Short hold + auto-restock: 72-hour pickup SLA is standard. After SLA, agent auto-cancels and triggers restock event back to availability service.

Store Capacity Model

store_capacity:
  store_id: BLR-042
  windows:
    - hour: 09  picks_per_hr: 30  reserved: 22
    - hour: 10  picks_per_hr: 30  reserved: 18
  current_load_pct: 73
  cutoff_for_today: 18:00
  next_available_window: tomorrow 09:00
Why this beats vanilla Sterling BOPIS

Sterling supports BOPIS out of the box (sourcing rules, ShipNode = store), but it doesn't model real-time store capacity, SLA-driven UI promises, or low-latency store-level availability. You add those around Sterling, not in it.

SD-04

Real-time Inventory Sync

EDA · Bi-directional

Problem

Inventory updates flow in from multiple authoritative sources: WMS (DC pick/pack/receive), store POS (sales, returns, cycle counts), 3PLs (drop-ship vendors), marketplaces (consumed inventory). Sterling GIV must be reconciled to these continuously. Conversely, downstream systems (search index, recommendation engine, marketplace listings) need GIV state. Sync must be near real-time, idempotent, ordered per SKU+node, and resilient to source outages.

Idempotency & Ordering — The Hard Part

  • Partition key = {sku}#{node_id} ensures all deltas for a SKU at a location land in the same Kafka partition → strict per-key ordering.
  • Sequence numbers: Each source attaches a monotonic source_seq. Reconciler skips deltas with seq <= last_processed_seq per {sku, node, source}.
  • Out-of-order tolerance: If seq=105 arrives before seq=104, buffer briefly (Kafka Streams windowed state store) — most cases self-resolve in seconds.
  • Compensating drift: A daily reconciliation job snapshots WMS + GIV and fixes drift. Alerts if drift > 0.1% of SKUs.

Fig SD4.2 — WMS → GIV Sync
%%{init: {'theme':'dark'}}%% sequenceDiagram participant W as WMS participant CDC as Debezium participant K as Kafka participant N as Normalizer participant R as Reconciler participant G as Sterling GIV W->>CDC: TX: pick 5 units SKU=A node=DC01 CDC->>K: inventory.delta {sku:A, node:DC01, qty:-5, seq:1042} K->>N: consume (partition by sku+node) N->>N: validate, unit conv (CASE→EA) N->>R: normalized delta R->>R: check last_seq < 1042 ✓ R->>G: adjustInventory(SKU=A, node=DC01, delta=-5) G-->>R: ack R->>R: persist last_seq=1042
Common pitfall — duplicate adjustments

If you don't track sequence numbers per-source, a Kafka consumer rebalance can replay messages and double-decrement GIV. Always store (sku, node, source) → max_seq in a Postgres dedup table or RocksDB state store.

SD-05

Marketplace OMS

Multi-tenant · 3P sellers

Problem

You run a marketplace where 3rd-party sellers list inventory alongside your 1P stock. The OMS must: (1) onboard sellers, (2) ingest their inventory feeds, (3) route orders to the right seller, (4) track seller-side fulfillment, (5) reconcile commissions and payouts, (6) handle SLA breaches and cancellations. Sterling alone is single-tenant — extending to multi-seller requires careful modeling.

Critical Design Choices

  • Sub-order model: Parent order → child orders per seller. Sterling handles 1P child; seller OMS handles each 3P child. Customer sees one order ID.
  • Inventory namespacing: inventory_owner is a first-class field. 1P stock in GIV; 3P stock in a separate Cassandra/Postgres store with seller-supplied feeds.
  • SLA enforcement: Each seller has SLA (e.g., dispatch within 24h). Orchestrator escalates / cancels and reroutes if breached.
  • Settlement decoupled: Don't tangle order processing with finance. Emit order.delivered events → settlement service computes commission, GST, TDS, and ERP entries asynchronously.
Why not put 3P inventory in Sterling GIV?

3P inventory updates faster, has lower trust, and follows different reconciliation rules. Putting it in GIV pollutes your 1P operational data and forces a single tenancy model. Keep them separate; the order router unifies the customer experience.

SD-06

Returns Platform

Reverse logistics · Fraud-aware

Problem

Returns in retail run 15–35% of online orders. Sterling supports returns natively (createReturnOrder, YFS_ORDER_HEADER.OrderType=RETURN) but a modern returns platform must handle: self-service initiation, reason capture, eligibility rules, RMA generation, reverse logistics pickup, multi-step QC at warehouse, refund vs exchange vs store credit, fraud detection, and analytics back to merchandising.

Critical Design Choices

  • Eligibility as a rules engine: Drools/Camunda rule sets per category, channel, customer tier. "Apparel: 30 days, with tags"; "Electronics: 7 days, sealed box only". Externalize so merch teams change rules without deploys.
  • Fraud scoring at initiation: ML model on customer return rate, order velocity, IP/device, item value. High-risk → manual review queue, not auto-approve.
  • Disposition ≠ Restock: Don't restock blindly. QC grades drive outcomes: A → resell, B → outlet, C → liquidator, D → write-off. Each path is a separate inventory movement.
  • Refund timing options: Instant refund (trust-based, for top-tier customers) vs. on-receipt (default) vs. on-QC-pass (high-fraud risk segment).
  • Reason codes feed merchandising: "Wrong size — 38% of dress returns" drives size-chart fixes. The returns platform is also a product-quality signal pipeline.
SD-07

Ship-from-Store Architecture

Network optimization

Problem

Treat 1500+ stores as mini-DCs. Benefits: faster delivery, reduced split shipments, leverages dead inventory in low-foot-traffic stores. Risks: store associates aren't packers, capacity is unpredictable, and shipping from a store can break customer experience (delays, cancellations) if poorly managed. Sterling supports SFS via sourcing rules + ShipNode = StoreNode, but the architecture around it determines whether it scales or implodes.

Sourcing Cost Function (the heart of SFS)

cost(node, order) =
    α · ship_distance_km
  + β · ship_carrier_cost
  + γ · split_shipment_penalty   // discourage 3-package fulfillment
  + δ · markdown_risk(node, sku) // dead stock at this store?
  - ε · store_perf_score(node)   // reliable stores get priority
  + θ · capacity_pressure(node)  // already at 80% load? penalize

minimize Σ cost over all line-items
subject to:
  - inventory_available(node, sku) ≥ qty
  - store_capacity_remaining(node) ≥ 0
  - ship_sla_meetable(node, customer)

Fig SD7.2 — Sourcing Decision + Store Pick
%%{init: {'theme':'dark'}}%% sequenceDiagram participant O as Order Svc participant SR as Sourcing Engine participant S as Sterling participant SA as Store App participant C as Carrier O->>SR: source(order) SR->>SR: evaluate DCs + 1500 stores SR-->>O: optimal: STR_BLR042 O->>S: createOrder + ShipNode=BLR042 S->>SA: pick task SA->>SA: associate picks (10 min SLA) SA->>S: confirmPick S->>SA: print label (Sterling integ w/ carrier) SA->>C: handoff at next pickup C-->>S: shipment.in_transit

Operational Guardrails

  • Per-store cancellation rate ceiling: If store rejects > 5% of pick tasks (out-of-stock, can't find item), auto-reduce its sourcing eligibility for 24h.
  • Inventory buffer: Reserve 10–20% of store inventory for walk-in customers. Don't let online drain the floor.
  • Cutoff times: Stores have daily carrier pickup windows. Sourcing must factor cutoff — orders after 3pm route to next-day stores only.
  • Pack quality: Stores often pack worse than DCs. Train + audit; use a few "champion" stores for high-value items.
Real-world incident pattern

A store does inventory cycle count → finds 8 fewer units than GIV says → 12 already-released SFS orders get cancelled in 5 minutes → angry customers, brand damage. Mitigation: dampen GIV trust on store nodes (hold-back factor of 0.9), and don't auto-source SFS for orders > ₹10K without DC fallback.

SD-08

Distributed Reservation System

Strong consistency

Problem

Reservations are the crux of oversell prevention. When a customer adds-to-cart or pays, you "hold" inventory across many possible nodes. The system must be: (1) strongly consistent per {sku, node}, (2) low-latency (<50ms), (3) auto-expiring (cart abandoned → release), (4) idempotent (retry-safe), and (5) able to do partial / cross-node reservations for split shipments.

Consistency & Sharding

  • Shard key = {sku}#{node_id}: All operations on a SKU at a node are serialized to a single shard → strong consistency without distributed locks.
  • Atomic Redis ops: Use DECRBY with Lua script to check-then-decrement under one round-trip. Reject negative results.
  • Postgres WAL: Every reservation event written to Postgres as durable log (with reservation_id unique constraint = idempotency). Redis is the hot view; Postgres is recovery.
  • Cross-shard reservations: For multi-line / multi-node holds, use a 2-phase pattern: (a) try-reserve all shards, (b) if any fails, compensating release of acquired holds. The orchestrator (Temporal) handles this saga.
  • Don't reserve in Sterling GIV directly: GIV demand inserts are too slow (~50ms/row + lock contention). Sterling sees only committed orders.
Why not just use Sterling reservations?

Sterling's reserveAvailableInventory writes to YFS_INVENTORY_DEMAND. At 1000 reservations/second this becomes the #1 lock contention source on Oracle. A dedicated reservation service offloads 95% of holds (cart-level), and only commits the survivors to GIV.

Race conditions you must address

  • Last-unit race: Two customers add the last unit simultaneously. Solved by atomic Redis DECRBY in reservation service.
  • Cart-vs-cart: Customer A holds; B sees zero; A abandons; B's cached PDP still shows zero for 30s. Solved by L1 cache TTL ≤ 30s + invalidation events.
  • Reservation-vs-WMS-cycle-count: WMS reports 5 fewer than GIV; orders already reserved. Solved by hold-back buffer + immediate event-driven re-evaluation.
  • Split-shipment partial reserve: Reserved 1 at DC + 1 at store; store's failed. Solved by saga-style compensating release of DC reservation, then re-source.
The trade-off you must verbalize

More aggressive oversell prevention = more "out of stock" shown to real customers = lost revenue. The right balance depends on margin and brand: luxury brands tolerate < 0.1% oversell at the cost of 5% lost sales; commodity retailers accept higher oversell for lower lost-sale rate. Always ask the interviewer for the brand's tolerance.

Q4How do you scale inventory availability?
+

Elevator answer

Treat it as a read-heavy CQRS problem. Sterling GIV is the write side. Build a 3-tier cache (in-process → Redis cluster → DynamoDB) fed by event-driven invalidation from RTAM, partition by {sku}#{pincode}, pre-aggregate node rollups, and serve from the closest tier. Scale each tier independently; don't let any read traffic reach Sterling RTAM.

Architect depth — scaling math

Workload characterization:

Peak PDP traffic        : 50,000 RPS
SKU x pincode space     : 5M SKUs × 30K pincodes ≈ 150B combinations
Realistic working set   : 10M hot keys (top SKUs × top pincodes)
Avg payload             : 200 bytes / response
Read amplification      : 1 PDP view = 5 availability calls (variants, recommendations)

Cache target hit rates  : L1 80% · L2 95% · L3 99.5% · GIV 0.5%
Sterling RTAM ceiling   : ~500 RPS sustained (DB-bound)
=> Cache must absorb 99% of traffic = 49.5K RPS

Storage tiers:

Key design moves:

  1. Pre-aggregation: For PDP, the question is "is this SKU available for ship-to PIN 560001?" — not "what's the qty in DC01 and STR_BLR042 and STR_BLR099?". Pre-compute the answer keyed by {sku}#{pincode} and refresh on inventory deltas.
  2. Stale-while-revalidate: Return cached value immediately, async-refresh in background if older than threshold. PDP correctness is "good enough at 30s old."
  3. Graceful degradation: If L2 is down, fall through to L3. If L3 is down, return last-known-good with a warning flag. Never call RTAM under load.
  4. Per-region read replicas: Replicate L3 (DynamoDB Global Tables) so each region serves locally; reduces tail latency and provides region-failover.
  5. Bulk APIs: POST /availability/bulk accepts up to 100 SKUs; reduces per-call overhead for category pages and search.
  6. Negative caching: Cache "out of stock" results too — they're equally valid.

Event-driven freshness

  • Sterling RTAM agent publishes INVENTORY_CHANGE events on every supply or demand change.
  • MQ → Kafka bridge, partition by {sku}#{node}.
  • Sync consumer recomputes {sku}#{pincode} rollups (it knows which pincodes are served from each node).
  • Updates DynamoDB; emits invalidation event to L2/L1.
  • Target P99 propagation: 2 seconds. Operationally critical: monitor consumer lag; alert at > 30s.
Scaling pitfall — the "hot SKU" problem

During a promo, 1 SKU gets 30% of all availability traffic. L1 cache absorbs it (good), but on a deploy / pod restart, all pods cold-start and hammer L2 simultaneously (thundering herd). Mitigations: warmup hooks, request coalescing per pod (singleflight pattern), and L2 read-replicas.

Common follow-ups

  • "What's your cache invalidation strategy?" → event-driven (preferred) + TTL fallback (safety net)
  • "How does this work cross-region?" → DynamoDB Global Tables; Kafka MirrorMaker for events; tolerate sub-second cross-region staleness
  • "What if the PIN code lookup is wrong?" → rollups are computed by serviceability rules; reconcile nightly with carrier ZIP coverage data
Q5How would you design BOPIS?
+

Elevator answer

BOPIS is a store-aware availability + capacity + workflow problem. Show only stores with the SKU in stock and pickup capacity within SLA. Reserve hard at order time against the chosen store. Route a pick task via Sterling pipeline to the store associate app. Track ready/picked-up state, with auto-cancel at 72h no-show. The hard parts are store capacity modeling and graceful failure when the store can't fulfill.

  • Each store has a picks_per_hour ceiling — typically 20–60.
  • Ceiling varies by hour, by day-of-week, by season. Tuesday 11am ≠ Saturday 2pm.
  • Capacity is shared with SFS picks. Holistic model needed.
  • When capacity is full, push pickup-ready ETA to next available window — show that to customer pre-purchase.
  • Real-time decrement on pick task creation; restore on pick complete or task expire.

  • Store can't find item: Associate marks "OOS"; orchestration triggers — (a) auto-substitute (only if customer pre-consented), (b) re-source to nearest store with stock, (c) cancel + refund. Customer notified at each step.

Topic design principles

  • One topic per domain event: order.captured, order.released, inventory.delta. Don't dump everything in one mega-topic.
  • Partition key = aggregate ID: order events keyed by order_id; inventory deltas by {sku}#{node}. Guarantees per-aggregate ordering.
  • Retention = 7 days minimum for replay; some topics (financial events) → 30+ days or compacted.
  • Schema Registry mandatory: Avro/Protobuf with backward+forward compatibility rules. Prevents the dreaded "consumer can't parse new producer message."

Sterling ↔ Kafka bridging — the practical reality

Sterling's native event mechanism is YIF transactions + MQ topics/queues. Three patterns:

  1. MQ → Kafka bridge (Camel/Kafka Connect MQ source connector): drains Sterling's outbound MQ, republishes to Kafka. Most events flow this way.
  2. Debezium CDC: For events Sterling doesn't publish but you need (e.g., specific status transitions, custom column changes). Reads Oracle redo logs.
  3. Outbox pattern (when you can modify Sterling): Sterling user exit writes events to an outbox table; Debezium publishes from there. Cleanest for bidirectional consistency.

Consumer patterns

  • Idempotent consumers: Use event_id dedup table or Kafka's transactional reads. Critical for DB writes.
  • Lag monitoring: Per-consumer-group lag SLO (e.g., < 30s for inventory.delta). Alerts trigger autoscale.
  • DLQ + retry topic: Failed messages → retry topic with delay; after N retries → DLQ for manual triage.
  • Co-partitioning: When joining two streams (orders + customers), they must share partition key. Kafka Streams enforces this at join time.

What Kafka is NOT for in OMS

  • Synchronous request/response: Don't use Kafka for "is this SKU available right now?" — use REST + cache.
  • Workflow orchestration: Kafka choreography breaks down beyond 4-5 steps. Use Temporal/Camunda for true workflows.
  • Source of truth: Kafka is a transport, not a database. Materialized views are derived state.

Common follow-ups

  • "How do you handle out-of-order events?" → partition key ensures per-key order; if cross-key ordering matters, use windowed joins in Kafka Streams
  • "What's your DR strategy for Kafka?" → MirrorMaker 2.0 to secondary region; consumers fail over with reset to last committed offset
  • "How do you migrate consumers without losing messages?" → blue/green consumer groups with dual-read, then cutover offset
  • "Why not RabbitMQ?" → throughput (Kafka 10× higher), retention/replay, partition ordering, ecosystem (Connect, Streams, ksqlDB)

Six attack vectors in detail

1. CQRS for reads

  • Availability → DynamoDB (see SD-01).
  • Customer order list → Elasticsearch (search + filter).
  • Goal: 0 RPS of vanilla read traffic from web/mobile reaches Sterling Oracle.

2. Externalize reservations

  • Cart-level holds in Redis (see SD-08).
  • Sterling YFS_INVENTORY_DEMAND only sees committed orders → typically 5-10× lower insert rate.
  • Frees up DEMAND-table buffer cache and reduces redo log volume.

3. YFS_TASK_Q hot-spotting

  • YFS_TASK_Q is shared by all task-queue agents. Concurrent SELECT ... FOR UPDATE SKIP LOCKED from many agents = serialization.
  • Mitigations:
    • Narrow agent criteria so each picks fewer rows (less lock contention).
    • Increase agent count + reduce per-agent batch size.
    • List partition YFS_TASK_Q by TASKQ_TYPE — agents touch only their partition.
    • Use LockID-based pessimistic locking strategy.
    • Consider EOF (End-of-Feed) pattern: separate priority lanes for SLA-critical tasks.
  • Sterling 10.x has improvements here vs 9.3 — upgrade if you can.

4. Bulk APIs

  • Sterling APIs accept multi-order payloads: multiApi wrapping multiple changeOrder calls in one transaction.
  • Reduces round-trips and per-call session overhead.
  • Carefully bound batch size (50–200) to avoid long-running transactions.

5. Archive cold orders aggressively

  • Sterling's purge agent (PurgeOrder) is your friend — run it daily.
  • Archive to a separate schema/database after 90 days; query-redirect for historical lookups.
  • Smaller hot tables = better buffer cache hit + faster query plans.
  • Range partition YFS_ORDER_HEADER by month — partition prune helps queries naturally.

6. Oracle-level tuning

  • Maintain optimizer stats freshness on hot tables (gather every few hours during peak).
  • Index review — Sterling ships generic indexes; profile your workload and add covering indexes.
  • Adaptive cursor sharing for skewed data.
  • Resource Manager to throttle reporting queries during OLTP peak.
  • Consider Oracle RAC for horizontal scale; Sterling supports it.

Interview Cheat Sheet — Director / Principal Architect

Top 5 clarifying questions to ask before drawing

  1. "What's the order volume — peak vs average?" 10K/day vs 1M/day completely changes the architecture.
  2. "Sterling 9.x or 10.x? On-prem WAS or OpenShift?" Determines containerization options and agent scaling levers.
  3. "How many channels — web only, or also marketplaces, stores, B2B?" Multi-channel changes the orchestration story.
  4. "What's the brand's tolerance for oversell vs lost-sale?" Drives the conservatism of availability and reservations.
  5. "What's the team's modernization budget — 6 months tactical or 18-month strategic?" Strangler Fig vs rip-and-replace decision.

Key trade-offs to verbalize proactively

Consistency vs availability

Reservations: strong. Availability reads: eventual. Be explicit about which is which and why.

Sterling vs microservices

Sterling for state + audit; microservices for scale + UX. Don't fight Sterling; ring it.

Choreography vs orchestration

Kafka events for fan-out; Temporal for stateful workflows. Pure choreography breaks beyond 4 steps.

Real-time vs batch

Customer-facing = real-time (sub-second). Reconciliation, settlement, analytics = batch/streaming.

Build vs Buy

Build differentiating UX; buy commodity (tax, fraud, address). Sterling itself is "buy."

Cost vs performance

3-tier cache is cheaper than scaling Oracle. Ship-from-store is operational cost vs delivery speed.

"Wow" moments — show principal-level depth

  • YFS_TASK_Q partitioning: Knowing this is a hot table and what to do about it signals you've operated Sterling, not just designed around it.
  • RTAM vs availability service distinction: Most people confuse Sterling's real-time inventory APIs with the availability service. Drawing the layer separation cleanly is principal-level.
  • Sourcing cost function math: Showing the multi-objective optimization with weights and constraints (not just "Drools") signals you've actually architected SFS at scale.
  • Reservation-aware PDP display: Many architects forget L1 (the customer-facing display) when discussing oversell. Mentioning safety buffers + active reservation subtraction is sharp.
  • Sterling AWR analysis: Tying contention mitigation to specific Oracle wait events shows operational depth.

Common failure modes interviewers probe for

  • "Big bang" replacement plans — they'll push back hard. Defend Strangler Fig.
  • Hand-waving "use Kafka" — they'll ask partition key, ordering, idempotency, DLQ. Have answers.
  • Ignoring stores — modern OMS is store-aware. If your design treats inventory as just DCs, you've failed.
  • Forgetting returns — 25–35% of online retail. A complete OMS architecture must address reverse logistics.
  • No DR / no observability — Director-level role, you must talk about MTTR, SLI/SLO, runbooks, chaos.
  • Only happy path — interviewers love asking "what happens when X fails?" Pre-empt with failure modes.

Questions to ask the interviewer at the end

  1. "What's the current Sterling pain point that's driving this hire — performance, modernization velocity, or cost?"
  2. "How is the Sterling platform team structured today, and how does it interact with the channel/product teams?"
  3. "What's the next 2-year roadmap for the OMS platform — and where does this role contribute?"
Final principle

At Architect-level interviews, depth beats breadth. Pick 2–3 areas you can go 5 levels deep in (e.g., reservations, availability scaling, modernization patterns) and steer probing questions there. Don't claim expertise you don't have — interviewers respect "I'd need to dig into that; here's how I'd approach it" far more than confident hand-waving.
